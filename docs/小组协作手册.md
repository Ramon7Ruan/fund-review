# 投后月度回顾工具 · 小组协作手册

> 这份文件是给全组看的操作规范。有疑问先翻这里，翻不到再问。

---

## 一句话流程

框架和核心由组长先搭好并锁死 → 每人认领一个模块端到端负责 → 外围功能挂在任务板上自由领 → 每周按里程碑验收 → 所有改动走短分支 + PR。

---

## 角色

| 角色 | 人 | 做什么 |
|---|---|---|
| 架构负责人 | 组长 | 定数据模型、目录、扩展点；review 所有 PR；合并主干 |
| 模块 Owner | 6 人 | 各自模块的设计与实现，对本模块质量负责 |
| 任务认领人 | 所有人 | 在任务板上领外围任务（新视图、新数据源、新算法） |

模块 Owner 是固定的，任务认领是流动的。一个人可以既是某个模块的 Owner，同时领别的模块的任务。

---

## 目录约定

```
src/
  core/           数据模型、类型定义        ← 锁定，改动需组长同意
  data/           数据源适配器              ← 一个源一个文件
  engine/
    returns/      收益计算                  ← 含分红复权
    attribution/  归因算法                  ← 一个算法一个文件
  views/          页面与视图                ← 一个视图一个文件
  ui/             通用组件
  registry.ts     功能注册表                ← 新功能在这里登记一行
```

**规矩：只改自己模块目录下的文件。** 需要动别人的文件，先在 issue 里 @ 对方，同意了再动。

新功能不要改核心，去 `registry.ts` 注册。这是全组冲突最少的地方。

## 分支与提交

```bash
git checkout main && git pull
git checkout -b feat/single-fund-attribution
# 开发……
git add -A && git commit -m "feat(attribution): 单基金行业归因"
git push -u origin feat/single-fund-attribution
```

- 分支名：`feat/xxx`、`fix/xxx`、`docs/xxx`
- **分支活不过 3 天**。三天做不完就拆成两个 PR。
- 提交信息：`类型(模块): 做了什么`，类型用 feat / fix / refactor / docs / test
- 一个 PR 不超过 400 行改动

## 任务卡模板

每张卡必须五栏齐。缺一栏，认领人可以拒绝认领。

```
目标：一句话说清做完是什么样

验收标准：
- 输入 X，输出 Y，且 Z
- 图上出现 A、B 两条曲线
- 通过单元测试 test_attribution_*.py

涉及模块：src/engine/attribution/
依赖：需先完成 #12（持仓快照表结构）
规模：S（半天）/ M（1-2 天）/ L（3 天以上，必须拆）
```

写不出验收标准，说明这个任务还没想清楚，先别贴出来。

## PR 规矩

提 PR 时用这个结构：

```
## 做了什么
一句话。

## 关联任务
Closes #23

## 怎么验证
跑 `npm test` 全绿；打开 /review 页面能看到月度收益分解。

## 有没有动接口/数据模型
没有 / 有，改了 xxx，已同步给 @某人
```

合并条件（缺一不可）：

1. 至少 1 人 review 通过
2. CI 全绿
3. 没有未解决的 review 评论
4. 分支已同步 main（自己 rebase，别让组长解冲突）

合并方式统一 squash，让 main 上每个 commit 都是可运行状态。

## 怎么加一个新功能

以"加一个归因算法"为例，五步：

1. **建文件**：`src/engine/attribution/industry.py`（或 `.ts`）
2. **照抄样板**：复制 `attribution/_template.py`，里面有约定的函数签名和返回结构
3. **注册**：在 `registry.ts` 里加一行，填展示名、参数、对应组件
4. **自测**：跑对账测试 `test_reconciliation`，分项之和必须等于组合实际收益
5. **提 PR**：按上面的模板写，找组长 review

第 4 步是硬要求。归因算法不过对账，不合。

## 每周节奏

| 时间 | 动作 | 时长 |
|---|---|---|
| 周一 | 同步会：本周目标 + 有没有接口变更 | 30 min |
| 周三 | 算法评审：这周新增/修改的归因口径 | 15 min |
| 周五 | 合并日：清空 PR 队列，打 tag | 自行安排 |
| 每天 | 卡住了在群里说一声，不憋着 | — |

**周一那个会只说三件事**：上周做了什么、本周做什么、有没有改动接口或数据模型。第三件最重要——不说的代价是别人白干三天。

## 里程碑

| 版本 | 目标 | 验收 |
|---|---|---|
| v0.1 | 能导入持仓数据、画出净值曲线 | 打开页面能看到一条真实的净值线 |
| v0.2 | 能做单基金归因 | 选一只基金，看到收益拆解，对账残差 < 0.1% |
| v0.3 | 能生成月度回顾报告 | 点一下导出，得到一份完整的月度报告 |

每个版本必须**能当场演示**。演示不了的功能不算完成。

## 撞车了怎么办

| 情况 | 处理 |
|---|---|
| 两个人改了同一个文件 | 先到先得，后到的人 rebase 并手动合并；拿不准就一起看 |
| 改到别人的模块目录 | 立刻在 issue 里说明，别默默推上去 |
| 需要改数据模型 | 停手，先在群里说，组长定方案再动 |
| 主分支坏了（CI 红） | 谁弄红的谁修，修不好 revert，不许放着过夜 |
| 有人三天没提交 | 组长主动问，不要等到周会 |

---

## 三条底线

1. **不直接推 main。** 一切走 PR。
2. **不改别人的模块不打招呼。** 一句话的成本，省掉一周的返工。
3. **不通对账的归因算法不算完成。** 数字对不上，图再好看也是错的。
