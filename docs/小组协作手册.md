# 投后月度回顾工具 · 小组协作手册

> 这份文件是给全组看的操作规范。有疑问先翻这里，翻不到再问。

---

## 一句话流程

框架和核心由组长先搭好并锁死 → 每人认领一个模块端到端负责 → 外围功能挂在任务板上自由领 → 每周按里程碑验收 → 所有改动走短分支 + PR。

---

## 角色

| 角色 | 人 | 做什么 |
|---|---|---|
| 架构负责人 | 组长 | 定数据模型、目录、扩展点；review 所有 PR；合并主干 |
| 模块 Owner | 6 人 | 各自模块的设计与实现，对本模块质量负责 |
| 任务认领人 | 所有人 | 在任务板上领外围任务（新视图、新数据源、新算法） |

模块 Owner 是固定的，任务认领是流动的。一个人可以既是某个模块的 Owner，同时领别的模块的任务。

## 目录约定

```
engine/           纯计算：不碰网络、不碰数据库
  runtime/        插件契约与加载器           ← 锁定，改动需组长同意
  returns/        收益计算（含权重漂移）
  attribution/    归因算法类型与样板
  screening/      异动检测类型与样板
  plugins/        算法插件，一人一目录        ← 组员在这里新建目录
data_pipeline/    抓取、缓存、备用源切换      ← 一个数据源一个文件
api/              FastAPI 接口                ← 锁定，改动需组长同意
web/src/
  core/           请求封装与插件收集器         ← 锁定
  components/     通用组件（卡片、错误边界、图表）
  features/       前端视图插件，一人一目录     ← 组员在这里新建目录
tests/            后端测试                    ← 锁定，只有组长可改
```

**规矩：只在 `engine/plugins/<你的名字>/` 和 `web/src/features/<你的名字>/` 下新建目录。**
核心代码、测试与基建的改动需要组长批准；插件目录的新功能只需任意 1 人 approve + CI 全绿。

**新功能不需要注册。** 两个插件目录都是自动发现，不存在 `registry.ts` 这类公共文件，
也就不会因为大家改同一行而冲突。

## 分支与提交

```bash
git checkout main && git pull
git checkout -b feat/single-fund-attribution
# 开发……
git add -A && git commit -m "feat(attribution): 单基金行业归因"
git push -u origin feat/single-fund-attribution
```

- 分支名：`feat/xxx`、`fix/xxx`、`docs/xxx`
- **分支尽量 5 天内合并**。超过 3 天还没做完，先同步一次 main（`git pull origin main` 或 rebase），不要攒到最后。做不完就把 PR 拆小。
- 提交信息：`类型(模块): 做了什么`，类型用 feat / fix / refactor / docs / test
- 一个 PR 尽量控制在 **800 行以内**。超过了在 PR 里说明原因即可，不用为了凑行数硬拆。

## 提交守则（硬性）

这五条和编程水平无关，是底线。做不到的 PR 直接打回。

1. **只改自己模块目录下的文件。** 要动别人的目录，先在 issue 里问。
2. **提交前跑 `make check`，全绿才能提 PR。** 它包含后端 lint 与测试、前端类型检查与测试、前端构建。红了不许提 PR。
   如果只是格式问题，跑 `make format` 一键修复，再检查一次。
3. **新增依赖要在 PR 里说明。** 加了什么库、为什么需要，由组长在 review 时确认并更新依赖清单。不要默默加完就走，别人本机缺库会跑不起来。
4. **禁止修改或删除测试断言。** 测试红说明代码有问题，不是测试有问题。改断言让 CI 变绿，等于把故障藏起来。
5. **PR 写清三件事**：改了什么、关联的任务卡（有就填 `Closes #N`，没有可留空）、`make check` 通过的证据（截图或粘贴输出）。

> 第 4 条为什么这么严：功能写不出来时，最省事的做法是把断言改成 `assert True`，CI 立刻全绿。所以 `tests/` 和测试文件在 CODEOWNERS 里只归组长，改这些文件必须组长批准。

## 任务卡模板

每张卡必须五栏齐。缺一栏，认领人可以拒绝认领。

```
目标：一句话说清做完是什么样

验收标准：
- 输入 X，输出 Y，且 Z
- 图上出现 A、B 两条曲线
- 通过单元测试（后端用例放 tests/ 或本包的 test_contract.py，前端放本目录的 *.test.ts）

涉及模块：engine/plugins/<你的名字>/ 与 web/src/features/<你的名字>/
依赖：需先完成 #12（持仓快照表结构）
规模：S（半天）/ M（1-2 天）/ L（3 天以上，必须拆）
```

写不出验收标准，说明这个任务还没想清楚，先别贴出来。

## PR 规矩

提 PR 时用这个结构：

```
## 做了什么
一句话。

## 关联任务
Closes #23

## 怎么验证
跑 `make check` 全绿；打开工作台页面能看到月度收益分解。

## 有没有动接口/数据模型
没有 / 有，改了 xxx，已同步给 @某人
```

合并条件（缺一不可）：

1. **核心代码、测试与基建**：组长 review 通过；**纯插件目录的新功能**：任意 1 人 approve 即可
2. CI 全绿（服务端强制，不绿无法合并）
3. 没有未解决的 review 评论
4. **建议**同步最新 main 以减少冲突；不强制要求 rebase
5. 没有修改测试断言

合并方式统一 squash，让 main 上每个 commit 都是可运行状态。

## 怎么加一个新功能

以"加一个归因算法"为例，五步：

1. **复制示例**：`cp -R engine/plugins/momentum_summary engine/plugins/你的功能名`，前端同样复制 `web/src/features/momentum-summary`。
2. **改三处名字**：后端 `PLUGIN.id`、前端 `manifest.id`、展示标题。两个 id 必须完全一致。
3. **写算法**：只改 `plugin.py` 里的 `run(ctx)`，纯函数，不碰网络与数据库。
4. **自测**：`make check` 全绿。归因类算法还必须过对账——分项之和等于组合实际收益，残差 < 0.1%。
5. **提 PR**：按上面的模板写，等组长 review。

第 4 步的对账是硬要求。归因算法不过对账，不合。

每一步的命令与常见问题见 [`如何新增一个功能.md`](./如何新增一个功能.md)。

## 每周节奏

| 时间 | 动作 | 时长 |
|---|---|---|
| 周一 | 同步会：本周目标 + 有没有接口变更 | 30 min |
| 周三 | 算法评审：这周新增/修改的归因口径 | 15 min |
| 周五 | 合并日：清空 PR 队列，打 tag | 自行安排 |
| 每天 | 卡住了在群里说一声，不憋着 | — |

**周一那个会只说三件事**：上周做了什么、本周做什么、有没有改动接口或数据模型。第三件最重要——不说的代价是别人白干三天。

## 里程碑

| 版本 | 目标 | 验收 |
|---|---|---|
| v0 | 基础代码框架：插件机制、数据层、工作台 | **已交付**（tag `v0`）。输入基金代码可看到真实净值曲线 |
| v0.1 | 能导入持仓数据、画出净值曲线 | 打开页面能看到一条真实的净值线 |
| v0.2 | 能做单基金归因 | 选一只基金，看到收益拆解，对账残差 < 0.1% |
| v0.3 | 能生成月度回顾报告 | 点一下导出，得到一份完整的月度报告 |

每个版本必须**能当场演示**。演示不了的功能不算完成。

## 撞车了怎么办

| 情况 | 处理 |
|---|---|
| 两个人改了同一个文件 | 先到先得，后到的人 rebase 并手动合并；拿不准就一起看 |
| 改到别人的模块目录 | 立刻在 issue 里说明，别默默推上去 |
| 需要改数据模型 | 停手，先在群里说，组长定方案再动 |
| 主分支坏了（CI 红） | 谁弄红的谁修，修不好 revert，不许放着过夜 |
| 有人三天没提交 | 组长主动问，不要等到周会 |

---

## 三条底线

1. **不直接推 main。** 一切走 PR。
2. **不改别人的模块不打招呼。** 一句话的成本，省掉一周的返工。
3. **不通对账的归因算法不算完成。** 数字对不上，图再好看也是错的。
